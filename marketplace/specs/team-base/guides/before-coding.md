# 开始写代码之前

逐项确认，任何一项答不上来，先问人，不要自行假设。

1. **目标：** 这个任务要解决什么问题？能用一句话说清吗？
2. **验收标准：** 怎样才算做完？正常、错误和权限场景分别是什么？
3. **非范围：** 这次明确不做什么？
4. **需求来源：** 需求写在哪里？Issue、`docs/prd/` 还是 `openspec/changes/`？
5. **已有实现：** 项目里有没有类似的功能或公共模块可以复用？先搜索。
6. **相关规范：** 读了对应目录的 `index.md` 吗？
7. **影响范围：** 会改哪些模块？会不会改接口、数据库结构、权限或配置？
8. **风险级别：** 是否涉及登录、权限、支付、计费、数据删除、破坏性或大表的数据库迁移（改名、删除、改类型、回填数据、给大表加索引）、CI 或生产配置？涉及时属于 L3，需要技术负责人审查和回滚方案。只新增表或可空字段的迁移属于 L2，但不论级别都要由人确认后再执行；拿不准时按 L3 处理（《团队协作开发规范》v1.3 的 4.3 节）。
9. **验证方法：** 完成后用什么测试和手工步骤证明它是对的？

确认后，先写出计划：要改的文件、做法、风险和验证方法，等人确认后再动手。
