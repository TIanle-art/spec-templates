# AI 使用规范

## 工作方式

1. 一个任务一个会话，开始时提供 Issue、验收标准、非范围和相关规范。
2. AI 先说明计划和要改的文件，人确认后再大范围修改。
3. 小步实现，每一步都运行相关检查。
4. 完成后运行 `make check`，贴出真实结果。
5. 人亲自看完整的 diff，能解释每一处关键改动后再提 PR。

## 公司 Skill

| 场景 | Skill |
|---|---|
| 处理缺陷、测试或构建失败 | `team-systematic-debugging` |
| 准备说“完成了”、提交或创建 PR 之前 | `team-verification-before-completion` |
| 收到审查意见或修改要求 | `team-receiving-code-review` |

## AI 不能做的事

- 批准或合并 PR，打发布标签。
- 推送或强推 `main`、`release/*`。
- 操作生产数据库和生产服务器。
- 修改 CI、部署脚本、生产配置，除非任务明确要求并由技术负责人审查。

## 必须人工检查的常见问题

- 使用了不存在的 API 或依赖。
- 改了任务以外的文件，或重复实现了已有的功能。
- 测试只是在迎合实现，或者测试被修改、删除。
- 吞掉了异常，遗漏了权限检查。
- 声称完成，但没有实际运行检查。

## 停下来的时机

- 连续两次修复失败。
- 需求不清楚，或者有多种合理方案。
- 改动涉及登录、权限、支付、数据库迁移或生产配置。

这时由人重新分析，或者把当前状态写进任务文件后开新会话。

## 数据

不把密钥、生产数据和未经授权的客户资料发给 AI 工具。客户项目只使用合同允许的工具。
