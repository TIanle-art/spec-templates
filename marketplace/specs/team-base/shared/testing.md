# 测试规范

## 要求

| 层级 | 覆盖什么 | 什么时候必须写 |
|---|---|---|
| 单元测试 | 业务规则、工具函数 | 新增或修改逻辑时 |
| 接口测试 | 权限、参数校验、错误处理 | 新增或修改接口时 |
| 端到端测试 | 登录和核心业务流程 | 核心流程变化时 |
| AI 评估 | 固定样本上的结果质量 | 修改提示词、模型、解析或检索方式时 |

不设统一的覆盖率数字，优先保证权限、计费、数据隔离和核心流程。

## 好的测试

- 验证业务行为，而不是重复实现的细节。
- 测试名称说明场景和预期，例如 `test_member_cannot_delete_document`。
- 覆盖正常、错误和权限三类场景。
- 故意改错实现时，测试应该失败。
- 不依赖执行顺序、当前时间和外部网络；需要时使用固定数据和模拟服务。

## 修复缺陷

先写一个能复现问题的测试，确认它失败，再修复，确认它通过。

## 禁止

- 删除、跳过、注释掉或放宽测试来让 CI 通过。
- 修改断言去匹配错误的实现。
- 在测试中使用真实的客户数据或生产环境的密钥。

如果确实要修改已有测试，在 PR 中说明原因。
